# Архітектура Store WMS

Настільна програма для Windows: Python 3.13, інтерфейс PySide6 (Qt), база SQLite (режим WAL) через
SQLAlchemy 2 і міграції Alembic. Зроблено так, щоб пізніше перейти на центральну PostgreSQL без
переписування програми.

## Шари

```
wms/ui/        екрани і діалоги (PySide6)      -> викликає лише services
wms/services/  бізнес-логіка, правила складу    -> працює з моделями і сесіями бази
wms/db/        моделі (таблиці), міграції, тригери-захисти, підключення
SQLite файл    (пізніше PostgreSQL)
```

* **UI** не містить SQL і не відкриває сесій бази (перевіряє тест
  `test_screens_never_talk_to_the_database_directly`). Екрани лише збирають введене і показують
  результат.
* **Services** — єдине місце правил: що можна провести, хто може, які перевірки. Сканер штрихкодів
  і ручний пошук користуються тими самими сервісами (окремої логіки для сканера немає).
* **DB** — `Database.session()` дає одну транзакцію на операцію: усе або нічого.
  `Database.migrate()` створює нову базу або оновлює стару до останньої версії.

## Ключові рішення

| Рішення | Чому |
|---|---|
| Запаси змінює лише `StockEngine.post` | Одна точка, де кількість змінюється; жоден екран чи сервіс не може «тихо» поправити цифру. Див. docs/STOCK_LEDGER.md |
| Журнал рухів і аудит — лише додавання (тригери бази) | Історію не можна підправити навіть інструментом для бази |
| Поточні залишки зберігаються окремо (`stock_levels`) і звіряються з журналом | Екрани швидкі (не треба сумувати 100 000 рухів), а перевірка цілісності доводить, що цифри правильні |
| Помилки виправляються сторном, а не редагуванням | Видно і помилку, і виправлення, хто і чому |
| Знімки назв у рухах і документах (v1.3) | Перейменування чи архівування комірки, проєкту, товару не змінює історію. Див. docs/HISTORY.md |
| Довідники не видаляються, якщо мають історію, а архівуються | Те саме |
| Кількість — ціле число тисячних, гроші — ціле число 1/10 000 GBP | Без похибок округлення з плаваючою комою |
| Отримано / залишилось по PO не зберігається, а рахується з проведених накладних | Цифри замовлення не можуть розійтися зі складом; сторно накладної автоматично повертає кількість «в дорогу» |
| Захист від подвійного збереження через `client_token` | Одна фізична операція = один рух, навіть при подвійному кліку чи повторному скані |
| SQLite `BEGIN IMMEDIATE` | Дві копії програми на одній базі не змішують операції |
| Правила цілісності і в коді, і в базі (FK, UNIQUE, CHECK, тригери) | Не залежимо лише від перевірок у формах |

## Перехід на PostgreSQL (майбутнє)

Що вже готово: моделі і запити — SQLAlchemy (без SQL, специфічного для SQLite, у сервісах);
тригери-захисти мають версію для PostgreSQL (`wms/db/engine.py`); адреса бази — один параметр
(`database_url` у налаштуваннях). Що треба буде зробити: сервер PostgreSQL, перенести дані,
перевірити блокування при одночасній роботі кількох ПК (`with_for_update` уже використовується).

## Чого свідомо немає

Мікросервісів, хмари, веб-сервера, бухгалтерії, CRM, інтернет-магазину. Це складська програма для
швидкої щоденної роботи на ПК складу.

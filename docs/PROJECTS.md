# Project Tree — Менеджер → Проєкт → Блок → Рівень → Юніт → Матеріали (v1.15)

Екран **PROJECTS ▸ Projects** (до v1.16 — «Project Tree»; таблиця проєктів тепер кнопка **Project List**). Показує і редагує структуру:

```
▼ John Smith                         (менеджер)
  ▼ Tribeca              TRI-01      (проєкт)
    ▼ Block A            A           (блок / корпус)
      ▼ Level 1          L1          (рівень / поверх)
        ▼ Kitchen        K01   24    (юніт: 24 кухні на цьому поверсі)
            H3311 Board  H3311  3 / unit   72 SHEET   (матеріал: 3 на кухню → 72)
            Hinge XYZ    HINGE  8 / unit  192 EA
        ▶ Wardrobe       W02   12
      ▶ Level 2          L2
    ▶ Block B
    ▶ Reception Desk     R01    1    (юніт прямо в проєкті, без блоку)
▶ Anna Lee
▶ Unassigned projects               (проєкти без менеджера)
```

**Блок і Рівень — необов'язкові.** Юніт може лежати прямо в проєкті (як раніше) або на рівні
блоку. Невеликий проєкт можна вести без блоків, великий житловий комплекс — Block A / Level 1…12.
У проєкті спочатку йдуть блоки, потім юніти, що лежать прямо в ньому.

Кількість менеджерів, проєктів, блоків, рівнів, юнітів і матеріалів нічим не обмежена.

## Як це пов'язано з тим, що вже є

| Що | Як зроблено | Чому |
|---|---|---|
| **Проєкт** | Це той самий проєкт, що в **Projects** (таблиця `sites`): Goods Out, резерви, повернення, Remaining. Новий проєкт у дереві одразу доступний для видачі. | Жодних дублікатів: один проєкт — один запис. |
| **Менеджер** | Нова таблиця `managers`. Проєкт посилається на нього полем `sites.manager_id` (може бути порожнім). Ім'я менеджера також лишається в старому полі «Project manager» — список проєктів, пошук і експорт працюють як раніше. | Зв'язок за ID, не за ім'ям: перейменування менеджера нічого не ламає. |
| **Поле «Project manager» у картці проєкту** | Тепер це список менеджерів. Нове ім'я, введене вручну, створює менеджера. | Одне джерело правди. |
| **Блок** | Нова таблиця `project_blocks`: проєкт, назва, код, примітки, порядок. | — |
| **Рівень** | Нова таблиця `project_levels`: блок, назва, код, примітки, порядок. | — |
| **Юніт** | Нова таблиця `project_units`: проєкт, рівень (може бути порожнім — тоді юніт прямо в проєкті), назва, код, кількість, примітки, порядок. | Проєкт у юніта зберігається завжди, тож потреба проєкту рахується одним запитом незалежно від блоків. |
| **Матеріал юніта** | Нова таблиця `unit_materials`: посилання на **існуючий товар** + кількість на 1 юніт, VPK код, примітки, порядок. Товар не копіюється: той самий H3311 може бути в будь-якій кількості юнітів і проєктів. | Залишки, резерви, закупівлі вже прив'язані до товару — потім їх легко порівняти з потребою. |
| **Material list (Required) проєкту** з v1.12 | Саме він рахує **Remaining**. **З v1.16 Required іде за юнітами сам**: кожна зміна юнітів, їхньої кількості або матеріалів змінює Required рівно на цю різницю (колонка `units_qty` пам'ятає, скільки з Required прийшло з юнітів). Вписане або імпортоване вручну зверху лишається. Матеріал, якого ще не було в списку, додається. Завершені / скасовані / архівні проєкти не змінюються, при відновленні проєкт наздоганяє юніти. Кнопка **Reset Required to Units** робить Required рівно як у юнітах (прибирає ручні добавки). | При оновленні до v1.16 (міграція 0013) ваші цифри не змінюються; додаються лише матеріали з юнітів відкритих проєктів, яких у списку ще не було. |

## Розрахунок потреби

```
Required = Σ (кількість юнітів × кількість матеріалу на 1 юніт)
```

Підсумок **ніде не зберігається** — щоразу рахується з бази (`wms/services/project_demand.py`),
тому не може розійтися зі структурою. Рахунок у цілих тисячних, без похибок округлення.

Один і той самий розрахунок для: одного юніта, рівня, блоку, проєкту, менеджера (його відкриті проєкти), будь-якого
набору проєктів і **всіх відкритих проєктів** (кнопка **Material Demand...**). Він не залежить від
екрана, тож Dashboard, Remaining і звіти зможуть ним користуватися далі.

## Робота з деревом

* **Таблиця з колонками рівнів (з v1.17)**: перші п'ять колонок — **Project Manager**, **Project**,
  **Block**, **Level**, **Unit**, далі **Material**, Code / Ref, Qty, Total required, Details. Кожен рядок
  стоїть у колонці свого рівня: проєкт завжди в колонці Project, блок — у Block тощо. Ширину колонок можна
  міняти, перетягуючи край заголовка; довгі назви видно в підказці; якщо колонки не вміщаються, з'являється
  прокрутка вбік.
* **Заголовки Project Manager і Project — це команди розгортання** (не сортування і не фільтр, дані не
  змінюються, пошук і статус лишаються):
  * клік на **Project Manager** — згортає все: видно тільки менеджерів (і «Unassigned projects»);
  * клік на **Project** — розгортає всіх менеджерів і показує всі проєкти; блоки, рівні, юніти й
    матеріали згорнуті.
  * Кожен клік завжди дає той самий вигляд, незалежно від того, що було відкрито. Заголовки Block, Level,
    Unit нічого не роблять. Вибраний рядок лишається вибраним, навіть якщо його гілку згорнуто.
* **Активний проєкт (з v1.18)**: клік на будь-який рядок проєкту (проєкт, блок, рівень, юніт, матеріал)
  підсвічує світло-зеленим (#E8F5E9) усі видимі рядки цього проєкту на всю ширину. Клітинка, на яку
  клікнули, — у синій рамці. Менеджер не підсвічується. Розгорнули гілку — нові рядки теж зелені.
  Належність визначається за ID проєкту, без запитів до бази.
* **Панель праворуч ховається (з v1.18)**: кнопка **▸ / ◂** на правому краю таблиці. Стан пам'ятається на
  цьому ПК; вибір рядка панель не відкриває; невписане в панелі зберігається, поки вона схована.
* **Незбережені зміни (з v1.19)**: якщо в панелі праворуч щось змінено і не збережено, перед вибором
  іншого рядка, зміною пошуку / статусу, переходом на інший екран або закриттям програми з'являється
  вікно **Unsaved Changes**: Save Changes (зберегти; якщо помилка — лишаємося, вписане ціле), Discard
  Changes (забути), Cancel (лишитися). Нічого не змінено — нічого не питає.
* **Розгорнути / згорнути вручну** — стрілка або подвійний клік; кожен рівень окремо; «Expand / Collapse
  Branch» у меню рядка. Стрілка ▸ / ▾ стоїть перед назвою, у колонці рядка. Програма пам'ятає на цьому ПК, що було розгорнуто, і після
  перезапуску відкриває так само.
* **Змінити на місці**: подвійний клік по назві (менеджер, проєкт, блок, рівень, юніт), коду блоку,
  рівня чи юніта, кількості юніта
  або кількості матеріалу на 1 юніт. Enter — зберегти, Esc — скасувати. Помилкове значення не
  зберігається, повертається старе.
* **Панель праворуч** — усі поля вибраного рядка + розрахунок матеріалів (юніт, рівень, блок, проєкт,
  менеджер).
* **Меню дій** — права кнопка миші, **⋯** в кінці рядка або клавіша Menu:
  * Менеджер: Add Project, Edit, Move Up / Down, Delete.
  * Проєкт: Add Block, Add Unit (directly in project), Edit, Duplicate, Change Manager (інший менеджер або Unassign), Update Material
    List from Units, Open Project Record, Delete.
  * Блок: Add Level, Edit, Duplicate Block (з усіма рівнями, юнітами і матеріалами), Move Up / Down, Delete.
  * Рівень: Add Unit, Edit, **Duplicate Level** (копія поверху з усіма юнітами і матеріалами — зробили
    Level 1, скопіювали, перейменували на Level 2), Move Up / Down, Delete.
  * Юніт: Add Material, Edit, Change Quantity, Duplicate, Move Up / Down, **Move to...** (на інший рівень,
    в інший блок чи проєкт, або прямо в проєкт), Delete.
  * Матеріал: Edit Quantity, Replace, Move Up / Down, Open Material, Remove.
* **Клавіші**: Ctrl+↑ / Ctrl+↓ — перемістити рядок, Insert — додати дочірній, F2 — перейменувати,
  Delete — видалити.
* **Add Material**: пошук серед існуючих матеріалів (код, Product Number, штрихкод, назва, опис,
  бренд, постачальник), можна вибрати кілька (Ctrl+клік), одна кількість на 1 юніт, VPK код і примітки.
  Якщо цей матеріал уже мав VPK код на іншому рядку, програма його підставить.

Перетягування мишею (drag-and-drop) поки не зроблено — є Move Up / Move Down і Ctrl+↑/↓. Сервіс уже
має `set_unit_position(unit, index)`, тож перетягування можна додати пізніше без змін у базі.

## Пошук і фільтри

Пошук шукає в: імені менеджера, назві і коді проєкту, назві і коді блоку, рівня та юніта, коді товару, Product
Number, VPK коді, назві / описі / бренді матеріалу, примітках рядка. Під час пошуку дерево показує
лише гілки зі збігами, розгорнуті до них, а збіги підсвічені жовтим. Якщо збігів понад 400, гілки не
розгортаються самі (щоб не відкривати тисячі рядків) — розгорніть потрібну.

Фільтр: статус проєкту (за замовчуванням відкриті). Окремі списки «All managers» / «All projects»
прибрано у v1.17 — менеджера чи проєкт знаходять заголовками Project Manager / Project або пошуком.

## Захист від помилок

* **Видалення менеджера ніколи не видаляє проєкти.** Програма питає: залишити їх без менеджера
  (Unassigned) або передати іншому менеджеру.
* **Видалення проєкту** — та сама безпечна логіка, що й раніше: ніколи не використаний проєкт
  видаляється разом зі структурою (у підтвердженні написано, скільки юнітів і рядків матеріалів
  зникне); проєкт з історією (видачі, резерви, документи) лише архівується, структура зберігається.
* **Видалення юніта** з матеріалами — підтвердження з кількістю рядків.
* **Видалення рівня / блоку** — підтвердження з точною кількістю рівнів, юнітів і рядків матеріалів,
  що зникнуть разом з ним.
* Архівний проєкт — лише перегляд; спочатку Restore.
* Кожна дія — одна транзакція: або все, або нічого. Кожна зміна пишеться в журнал аудиту
  (MANAGER_*, BLOCK_*, LEVEL_*, UNIT_*, UNIT_MATERIAL_*, PROJECT_MANAGER_CHANGED, PROJECT_DUPLICATED).
* Нічого в цьому модулі не змінює залишки, рухи, Goods In / Out, повернення чи історію.
* Права: перегляд — «View sites / projects», зміни — «Manage sites / projects» (нові ролі не потрібні).

## Швидкість

Гілки читаються з бази лише при розгортанні; кількості рахуються в SQL. Індекси на всіх зв'язках
(`manager_id`, `site_id`, `block_id`, `level_id`, `unit_id`, `product_id`), порядку і кодах. Виміряно на 50 менеджерах,
300 проєктах, 3 000 юнітах і 30 000 рядках матеріалів (5 000 товарів):

| Операція | Час |
|---|---|
| Менеджери з кількістю проєктів | 5 мс |
| Проєкти одного менеджера / юніти проєкту / матеріали юніта | 3–7 мс |
| Пошук по всьому дереву | ~60 мс |
| Потреба одного проєкту / менеджера | 4–6 мс |
| Потреба всіх відкритих проєктів (30 000 рядків) | 50 мс |

## Що можна додати далі (структура вже готова)

Потреба проти залишку (Available) і дефіцит по проєкту, резерви під юніти, замовлено / отримано /
видано у виробництво / відправлено на об'єкт, відсоток готовності проєкту. Усе це — порівняння
`project_demand.demand_by_project(...)` з даними, які вже є (резерви, рухи, закупівлі), без нових
копій товарів.

## v1.23 — етап 1: модель даних для норм і зроблених юнітів

Перший етап модуля «проєкти → блоки → поверхи → юніти → норми». Лише база даних і сервіси, екрани —
наступними етапами. Наявна структура (менеджер, проєкт, необов'язкові блок і поверх, юніт, матеріали
юніта) лишається як була: її розширено, а не перебудовано.

| Що | Як зроблено | Чому |
|---|---|---|
| **Назва проєкту без дублікатів** | Назву вводить менеджер. Програма не дає створити або перейменувати проєкт на назву, яка вже є, навіть якщо вона написана іншими літерами, з зайвими пробілами чи через дефіс («Riverside Apartments» = «riverside  apartments» = «Riverside-Apartments»). Повідомлення каже, який проєкт уже має цю назву; якщо він в архіві — радить відновити його. Те саме при Duplicate Project і при створенні проєкту з Excel-імпорту. | Для порівняння зберігається «ключ» назви `sites.name_key` з індексом — перевірка миттєва на будь-якій кількості проєктів і однаково працює в SQLite і PostgreSQL. |
| **Старі дублікати** | Якщо у вашій базі вже є два проєкти з однаковою назвою, вони працюють як раніше і їх можна зберігати; перевірка спрацює лише тоді, коли назву змінюють. | Оновлення не має ламати наявні дані. |
| **Блоки й поверхи необов'язкові, юніт на поверсі** | Без змін з v1.15: юніт лежить на поверсі (`project_units.level_id`) або прямо в проєкті для простих проєктів. | — |
| **Норма матеріалу на один юніт з датою зміни** | Поточна норма — як і раніше `unit_materials.quantity_per_unit`. Нова таблиця `unit_material_norms` зберігає **кожне** значення норми: скільки, коли змінено, ким, причина і для кого зміна — **ALL** (усі юніти, вже зроблені перераховуються) чи **FUTURE** (лише ще не зроблені). Зміна кількості в дереві пишеться в історію як ALL — це поведінка, яка була досі. | Без історії неможливо відповісти «скільки матеріалу пішло на вже зроблені юніти», а це потрібно для етапу 4 (вікно «перерахувати зроблені чи лише майбутні»). |
| **Зроблені юніти** | Нова таблиця `unit_completions`: «зроблено / встановлено N юнітів цього типу такого-то числа». Запис не редагується; помилку **скасовують** (запис лишається в історії з причиною, але не рахується). Не можна відмітити більше, ніж лишилося зробити, і не можна зменшити кількість юнітів нижче вже зроблених. Юніт, поверх чи блок із зробленими юнітами не видаляється, доки ці записи не скасовано. | Як і зі складськими документами: історія не зникає. |

### Яку норму використали зроблені юніти

Одне правило: партія зроблених юнітів використала **останню норму, яка діяла на момент запису партії,
або пізнішу, якщо та змінювалась для ALL**. Приклад: кухня, 10 шт., норма 3 листи.

* Зроблено 4 кухні → норму змінено на 5 «лише для майбутніх» → потреба = 4 × 3 + 6 × 5 = **42**.
* Те саме, але «для всіх» → 10 × 5 = **50** (як Required зараз).

Поки немає зроблених юнітів, результат завжди = кількість × поточна норма, тобто цифри Required і
Remaining не змінюються. Розрахунок — `wms/services/unit_norms.py` (`UnitNormService.unit_needs`,
`project_needs`); на етапі 4 Required і звіти перейдуть на нього.

`unit_completions`. Кожен наявний рядок матеріалу отримує перший запис історії — свою поточну норму з
датою, коли рядок додали. Залишки, рухи, документи і Required не змінюються.

### Як це зберігається (без дублювання)

Рядки беруться прямо з Project → Block → Level → Unit. Відмітки — це ті самі записи `unit_completions`
з v1.23, до яких міграція **0016** додала `stage` (DONE / DISPATCHED / ON_SITE) і `piece_no` (номер
штуки). Тому відмітка «Done» на дашборді — це і є «зроблений юніт» для норм матеріалів. Відмітки не
редагуються і не видаляються: «змінити дату» = скасувати стару (причина «Date corrected») + нову з тим
самим часом запису, тож норма, з якою юніт зроблено, не змінюється. Скасувати можна лише останній етап
штуки. Юніт з будь-якими відмітками не видаляється, а його кількість не можна зменшити нижче найбільшого
відміченого номера штуки.

Якщо «зроблено N» записано для типу юніта загалом (без номера штуки), дашборд показує ці N на перших
штуках без власної відмітки; змінювати такий запис треба там, де його створили.

Поки що «Dispatched» ставиться вручну і не пов'язаний з Dispatch / Delivery Note (v1.22).

## v1.25 — Імпорт структури проєкту з Excel (Projects ▸ «Import from Excel...»)

Кнопка **Import from Excel...** на екрані Projects додає з однієї книги Excel проєкти, блоки, рівні,
юніти і (за бажанням) матеріали юнітів з нормою на 1 юніт. Код: `wms/services/structure_import.py`,
вікно `wms/ui/dialogs/structure_import.py`.

### Шаблон

«Download Excel template...» у вікні імпорту зберігає книгу з аркушами:

| Аркуш | Що в ньому |
|---|---|
| **Structure** | Один рядок — один юніт: Project Manager, Project Name, Project No *, Block, Level, Unit Code, Unit Name *, Quantity *, Notes. |
| **Materials** (необов'язковий) | Один рядок — один матеріал юніта: Project No *, Block, Level, Unit Code / Unit Name, Material Code *, Qty per Unit *, VPK Code, Notes. |
| How to fill in | Пояснення кожної колонки і правила. |
| Example | Заповнений приклад. Цей аркуш ніколи не імпортується. |

Колонки можна називати й інакше (Job No, Building, Floor, Unit, Qty, «Поверх», «Кількість»…), а заголовок
може бути не в першому рядку — програма знаходить його в перших 15 рядках. Рядок «Total» пропускається.

### Як зіставляється (регістр, пробіли і розділові знаки не важливі)

* **Проєкт** — за Project No. Номер, якого немає в WMS, створює новий проєкт (статус Planned); для нього
  потрібна Project Name, якої немає в іншого проєкту. Назву й менеджера наявного проєкту імпорт **не змінює**
  (у перевірці буде примітка).
* **Блок** — за назвою в проєкті, **рівень** — за назвою в блоці. Нові створюються в кінці списку.
  Block без Level — помилка (юніти лежать на рівні); обидва порожні — юніт прямо в проєкті.
* **Юніт** — за Unit Code у своєму місці, якщо код заповнений (або юніт з такою назвою без коду), інакше за
  Unit Name. Знайдений юніт оновлюється, лише якщо щось відрізняється (кількість, код, примітки).
* **Матеріал** — за кодом матеріалу в WMS. Матеріали тут не створюються: спочатку Materials ▸ Import.

### Перевірка перед імпортом

«Check» читає книгу й перевіряє кожен рядок, нічого не записуючи. Кожен рядок має статус **New / Update /
No change / Error** і зрозумілу причину. Помилки: порожні обов'язкові поля, не число, від'ємна кількість,
дубль юніта чи матеріалу в книзі, нова назва проєкту вже зайнята, архівний проєкт, матеріалу немає в WMS,
юніта для матеріалу немає ні в книзі, ні в WMS, кількість менша за вже зроблені юніти / відмічені штуки
на дашборді. **Поки є хоч одна помилка, Import недоступний**; «Export problems...» зберігає список у Excel.

### Імпорт

* Спочатку резервна копія (`*_safety.zip`), без неї імпорту не буде.
* Книга перевіряється ще раз; якщо з моменту перевірки щось змінилось (в книзі чи в WMS) — імпорт
  зупиняється і просить переглянути нову перевірку.
* Усе пишеться **однією транзакцією**: або все, або нічого (Cancel теж повертає все як було).
* **Нічого не видаляється і не переміщується.** Повторний імпорт тієї самої книги нічого не змінює.
* Залишки (stock) не змінюються. Required у списку матеріалів проєкту і Production Dashboard підхоплюють
  нові юніти одразу, як і при ручному додаванні в дереві. Зміна норми записується в історію норм (ALL).
* В журналі аудиту: SITE_CREATED, BLOCK_CREATED, LEVEL_CREATED, UNIT_CREATED / UNIT_UPDATED,
  UNIT_MATERIAL_ADDED / UPDATED і підсумок PROJECT_STRUCTURE_IMPORTED по кожному проєкту.

Міграції бази немає — використовуються таблиці v1.15–v1.24.

# Журнал руху запасів (Stock Ledger) — версія 1.4

**Головне правило:** кількість товару на складі змінюється лише одним шляхом: записом у журнал руху
(`stock_movements`). Кожна поточна цифра пояснюється історією рухів, і програма це перевіряє.

## 1. Як записується кожна операція

| Шар | Що там | Хто змінює |
|---|---|---|
| `stock_movements` — журнал | Один рядок на кожну фізичну зміну: товар, кількість, з якої комірки, в яку, проєкт, постачальник, документ, хто і коли, знімки назв | Лише `StockEngine.post` (`wms/services/stock_engine.py`). База забороняє UPDATE і DELETE |
| `stock_levels` — поточний залишок | Товар + комірка → кількість (для швидких екранів) | Лише `StockEngine`, у тій самій транзакції, що й рух |
| Документи (накладна, Goods Out, повернення, переміщення, коригування, виробництво, інвентаризація) | Шапка і рядки, кожен рядок посилається на свій рух | Сервіс документа. Проведений рядок база змінити не дає |

Залишки рахуються на трьох рівнях:

* **Товар + комірка** — таблиця `stock_levels`.
* **Товар + склад** — сума по комірках цього складу (склад = верхній рівень дерева локацій).
  `services.ledger.product_balance(...).by_warehouse`, `services.ledger.warehouse_balances()`.
* **Товар** — сума по всіх комірках (`on_hand`); окремо видно кількість у недоступних комірках
  (QUARANTINE тощо), яку не можна видати.

## 2. Типи рухів

Збережені значення ніколи не перейменовуються (інакше стара історія зламається). Назви зі
специфікації — синоніми (`MOVEMENT_TYPE_ALIASES` у `wms/core/enums.py`):

| Специфікація | Значення в базі | Напрям |
|---|---|---|
| GOODS_IN | `GOODS_IN` | у комірку |
| GOODS_OUT | `GOODS_OUT` | з комірки на проєкт |
| BIN_TRANSFER | `TRANSFER` | з комірки в комірку (загальна кількість не змінюється) |
| SITE_RETURN | `RETURN_FROM_SITE` | з проєкту в комірку |
| SUPPLIER_RETURN | `RETURN_TO_SUPPLIER` | з комірки постачальнику |
| ADJUSTMENT_IN / ADJUSTMENT_OUT | `ADJUSTMENT_IN` / `ADJUSTMENT_OUT` | ручне коригування з кодом причини |
| STOCKTAKE_ADJUSTMENT | `STOCKTAKE_ADJUSTMENT` (нове) | різниця затвердженої інвентаризації, + або − |
| PRODUCTION_CONSUMPTION | `PRODUCTION_CONSUME` | матеріал списано у виробництво |
| PRODUCTION_OUTPUT | `PRODUCTION_OUTPUT` | готовий виріб на склад |
| — | `OPENING_BALANCE` | початковий залишок при запуску |
| REVERSAL | див. розділ 3 | дзеркало оригіналу |

## 3. Сторнування (Reverse Transaction)

Проведений рух не редагується і не видаляється. Помилка виправляється **сторном**: новим рухом —
дзеркальним відображенням оригіналу.

```
Оригінал:  #1201 GOODS_OUT | H3311 | 20 | B04 → Project A
Сторно:    #1388 REVERSAL  | H3311 | 20 | Project A → B04   (reversal_of_id = 1201)
```

Обидва рядки лишаються в історії. Для кожного сторно в таблиці `movement_reversals` записано:

| Поле | Значення |
|---|---|
| `original_movement_id` | рух, який сторновано (original_transaction_id) |
| `reversal_movement_id` | рух-сторно (reversal_transaction_id) |
| `reason_code` + `reason` | код причини і пояснення (reversal_reason) |
| `reversed_by_id`, `reversed_by_name_snapshot` | хто (reversed_by) |
| `reversed_at` | коли (reversed_at) |

**Рішення щодо типу сторно.** Рядок-сторно зберігає тип оригіналу (наприклад `GOODS_OUT`) і
позначається посиланням `reversal_of_id`. На екрані він показується як «Reversal of Goods Out», а
фільтр «Reversal» знаходить усі сторно. Чому так: кожен звіт «скільки видано на проєкт», «скільки
прийнято від постачальника» автоматично віднімає сторно, бо вони того самого типу і з протилежним
напрямком. Якби тип був окремий (`REVERSAL`), кожен такий звіт треба було б переписати, і забута
умова тихо давала б неправильні цифри.

**Що де сторнується:**

* Накладна, Goods Out, повернення, виробництво — **цілим документом** (кнопка Reverse у документі).
  Так статус документа завжди збігається з його рухами.
* Переміщення між комірками і коригування — **по одному руху** (Stock Movements → відкрити рух →
  Reverse...).

**Правила, які тримає сама база** (а не лише програма, `wms.db.engine.ledger_trigger_sql`):

* рух сторнується лише один раз (унікальний індекс `uq_stock_movements_reversal_of`);
* сторно не можна сторнувати ще раз — треба провести новий рух;
* сторно мусить бути дзеркалом: той самий товар, та сама кількість, комірки навпаки;
* записи `movement_reversals` не можна змінити чи видалити.

## 4. Коди причин (Reason Codes)

Налаштовуються в **Settings → Reason codes**. Кожен код має місця використання: коригування,
сторно, повернення, розбіжності поставки. Код (наприклад `DAMAGED`) записується в документ і більше
не змінюється; назву можна перейменувати. Непотрібний код не видаляється, а «виводиться»
(Retired): зникає зі списків, старі записи показують його як раніше. Системні коди
(`STOCK_COUNT`, `OPENING_BALANCE`, `DATA_ENTRY_ERROR`, `OTHER`) вивести не можна.

Стандартні: Damaged, Missing, Stocktake Correction, Incorrect Delivery, Over-delivered, Rejected,
Returned from Project, Supplier Return, Scrap, Lost, Found, Data Entry Correction, Posted Twice,
Opening Balance, Other.

Причина обов'язкова для коригувань і сторно (код + текст пояснення).

## 5. Перевірка цілісності (Ledger = Current Stock)

**Settings → Data check → Run data check**, або `StoreWMS.exe --self-test`.
Код: `wms/services/integrity.py`. Перевіряє:

| Перевірка | Рівень |
|---|---|
| Залишок кожного товару в кожній комірці = сума рухів | CRITICAL |
| Загальний залишок кожного товару = сума рухів | CRITICAL |
| Залишок товару на кожному складі = сума рухів | CRITICAL |
| Кожне сторно має запис «хто / коли / чому» і навпаки | CRITICAL |
| Кожен проведений рядок документа має свій рух з тим самим товаром і кількістю | CRITICAL |
| Сторнований документ має сторновані всі рухи; проведений — жодного | CRITICAL |
| Від'ємний залишок (дозволений лише через записаний override) | WARNING |

Якщо є CRITICAL — цифрам на екрані довіряти не можна, доки причину не з'ясовано. Якщо проблема лише
в залишках (журнал цілий), **Rebuild stock levels from history** перераховує залишки з журналу.
Сам журнал ця кнопка не змінює.

## 6. Усе або нічого; захист від повторного збереження

* Кожна операція — одна транзакція бази: шапка документа, рядки, рухи, залишки, сторно-записи,
  журнал аудиту. Якщо будь-що падає — не зберігається нічого (тести
  `test_a_failure_at_the_last_step_leaves_nothing_behind`).
* SQLite працює в режимі `BEGIN IMMEDIATE` — дві копії програми не можуть провести операції
  впереміш.
* Подвійний клік Save, повторний Enter, повторний скан, повторне відкриття вже проведеної форми:
  кожна форма має `client_token`; другий раз той самий токен відхиляється («already posted»), а
  номер накладної від того самого постачальника — як дублікат.

# Store WMS — дорожня карта розвитку

Дата: 09.11.2026, на основі аудиту v1.19.0 ([повний аудит](STORE_WMS_FULL_AUDIT.md)).
**Нічого з цього ще не реалізовано.** Реалізація — лише після вашого затвердження, по одному
етапу = один PR, як у Phase 1.

Складність: **S** — до 1 дня роботи, **M** — 1–3 дні, **L** — 3–7 днів, **XL** — понад тиждень
(оцінка обсягу коду і тестів, не календарний термін).

## 4. Мобільний доступ — що потрібно в архітектурі

Зараз: настільна програма, SQLite, бізнес-логіка в `services/` без залежності від UI ✅ (це
головна перевага — мобільний клієнт може викликати ті самі правила).

Потрібно перед мобільним:
1. **Центральна PostgreSQL** (R-A3) — SQLite не підтримує кілька пристроїв по мережі.
2. **Невеликий сервер (API)** поверх `services/` — телефон не повинен підключатися до БД напряму
   (паролі, блокування, версії). Тонкий шар: вхід, 6–8 операцій.
3. **Блокування і конфлікти**: `with_for_update` вже є в ключових місцях; потрібно тестами
   перевірити одночасну видачу одного товару з двох пристроїв на PostgreSQL.
4. **Ідемпотентність**: `client_token` уже захищає від повторного скану/подвійної відправки ✅ —
   важливо для нестабільного Wi-Fi.
5. Сценарії мобільного (як у D365 mobile app, але мінімум): пошук комірки/товару, прийом за PO,
   видача з picking list, переміщення, підрахунок комірки, підтвердження доставки (POD-фото).

## 5. Xero — хто є джерелом даних

| Дані | Джерело правди | Напрям | Примітка |
|---|---|---|---|
| Постачальники (контакти) | **Xero** | Xero → WMS | Зіставлення за кодом/назвою (у WMS уже є нормалізація `supplier_key`) |
| Матеріали (коди, кількості) | **WMS** | WMS → Xero (опційно як Items без обліку запасу) | Кількості в Xero не ведемо, щоб не було двох залишків |
| Purchase Orders | **WMS** (операційні) | WMS → Xero | Номер PO WMS = Reference у Xero; повторна відправка за тим самим номером — оновлення, не дубль |
| Рахунки постачальників (bills) | **Xero** | Xero → WMS (лише статус/посилання) | Звірка: bill ↔ PO ↔ накладні Goods In |
| Вартість запасу | **WMS** рахує, **Xero** проводить | WMS → Xero (місячний журнал) | Не в реальному часі — менше розбіжностей |
| Фінзвітність | **Xero** | — | WMS не робить бухгалтерії |

Обов'язково: журнал синхронізації (що, коли, відповідь Xero), черга з повторними спробами при
збої API, ключі ідемпотентності (номер документа WMS), ручна кнопка «Re-sync», звіт розбіжностей.
Жодна синхронізація **не змінює запас** у WMS.

## 6. Ризики дорожньої карти

| Ризик | Як знизити |
|---|---|
| Перейменування Remaining зламає ваші Excel-шаблони | Рішення РІШ-1 до D1; у експорті — нові назви колонок одразу; описати в release notes |
| Масовий резерв створить сотні резервів помилково | Попередній перегляд + одна транзакція + масове «Release» за номером операції |
| Picking list сприймуть як вже видане | Чіткий статус «not issued», запас змінюється лише через Goods Out |
| Перехід на PostgreSQL | Спершу паралельний тестовий сервер, перенос з бекапу, перевірка Data check |
| Ширші списки вибору (пошук у БД) зламають сканер-потік | Тести сканера (`lines.py`) мають пройти без змін |

## 7. Рекомендоване перше завдання

**Етап A1 «Надійність»: карантин для пошкодженого + попередження про обрізані списки + політика
входу + захист незбережених змін у діалогах.**

Чому першим:
1. Тут єдиний знайдений **P0** щодо запасу (R-A1): пошкоджене зараз може стати Available і поїхати
   на об'єкт.
2. Обсяг малий (S–M), нових екранів немає, правила обліку не змінюються — швидко перевірити і злити.
3. Інші етапи (Planning, масовий резерв, picking list) додають нові форми; захист незбережених
   змін і чесні лічильники списків мають бути вже на місці.

**Одразу після A1** — етап **D1+D2 (Planning + масовий резерв)**: це найбільша щоденна економія
(резерв проєкту з N діалогів в 1). Якщо вам важливіша швидкість, ніж P0-виправлення, — можна
поміняти місцями; A1 тоді піде другим.

## 8. Підсумок

### Топ-10 UI/UX покращень
1. Project Material Planning як режим екрана Projects (R-P1).
2. Проєктні тривоги на Dashboard: дефіцит, «due in 7 days», over-issued (R-D1).
3. Екрани поміщаються в 1366×768 без прокрутки ключових колонок (R-UI4).
4. Миттєві списки вибору товару на великій базі (R-PF1).
5. Захист незбережених змін у всіх діалогах і формах (R-A5).
6. Чесні лічильники «перші N з M» і ледаче завантаження списків (R-A2, R-UI2).
7. Повне контекстне меню матеріалу: Transfer / Reserve / Label / Open bin (R-M1).
8. Компактні заголовки екранів (R-UI3).
9. Зрозуміле меню: Supplier Deliveries, Returns і Stocktake не в MORE (R-UI1).
10. Єдині статус-бейджі, токени кольорів, іконки (R-UI5).

### Топ-10 функціональних покращень
1. Масовий резерв «Reserve remaining» (R-P2).
2. Picking list + Load from project у Goods Out (R-W2).
3. To Purchase → чернетки PO для проєктів (R-P3).
4. Карантин для пошкодженого (R-A1).
5. Вихідні доставки + лист кур'єру + POD (R-L2).
6. Масовий Transfer / «Move whole bin» (R-W4).
7. Сканування в інвентаризації (R-W5).
8. Return to store з проєкту (R-W6).
9. Звіти: Outstanding, Supplier performance, Stocktake differences, Consumption, Valuation (R-R1–R-R3).
10. Damaged qty при прийомі (R-W1).

### Топ-5 автоматизацій
1. Виявлення дефіциту матеріалів проєктів (лічильник + To Purchase).
2. Picking list з потреби/резервів.
3. Чернетки PO з дефіциту проєктів (як Reorder Required — лише чернетки).
4. Чернетка листа кур'єру з даних проєкту.
5. Нагадування при вході: overdue PO, резерви «due», стан бекапу.

### Топ-5 критичних ризиків
1. Пошкоджене повернення стає Available (R-A1, P0).
2. Робота з однієї SQLite-бази з кількох ПК через мережевий диск (R-A3, P0 за умови 2+ ПК).
3. Мовчазне обрізання списків документів (R-A2).
4. Слабка політика входу на спільному ПК: короткий пароль, без блокування, без автовиходу (R-A4).
5. Різне розуміння «Remaining» між програмою і ТЗ — ризик неправильних рішень щодо закупівель (РІШ-1).

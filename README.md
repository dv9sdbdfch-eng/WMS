# Store WMS: складська програма для меблевого виробництва

Програма для Windows: облік матеріалів і готових виробів, прийом поставок (Goods In) з накладними та сканами,
видача на об'єкти (Goods Out), повернення, переміщення між комірками, коригування, виробництво, звіти з
експортом в Excel/CSV/PDF, повна історія рухів і журнал змін. Інтерфейс англійською (UK), гроші в £, метрика.

---

## 1. Як отримати інсталятор (один раз, ~15 хвилин)

Інсталятор для Windows збирається на будь-якому комп'ютері з Windows 10/11 (64-bit).

1. Встановіть **Python 3.13 (64-bit)** з <https://www.python.org/downloads/windows/>.
   На першому екрані інсталятора поставте галочку **"Add python.exe to PATH"**.
2. Встановіть **Inno Setup 6** з <https://jrsoftware.org/isdl.php> (усі параметри за замовчуванням).
3. Розпакуйте папку `store_wms` і двічі клацніть **`build.bat`**.
   Скрипт сам встановить потрібні бібліотеки, прожене автотести і збере програму.

Результат: **`dist\StoreWMS-Setup-1.15.0.exe`**. Цей файл можна копіювати на будь-який комп'ютер складу і
встановлювати звичайним способом (Next → Next → Finish). Python на цих комп'ютерах не потрібен.

> Якщо проєкт буде на GitHub, інсталятор збирається автоматично (файл `.github/workflows/build-windows.yml`):
> вкладка Actions → "Build Windows installer" → Run workflow.

## 2. Перший запуск

* Логін **admin**, пароль **admin**. Програма одразу попросить змінити пароль.
* **Settings → General**: вкажіть назву компанії (друкується у звітах і накладних) і папку для резервних копій.
* **Locations / Bins**: створіть свою структуру Warehouse → Zone → Rack → Shelf і комірки
  (кнопка "Create several bins" створює, наприклад, B01…B40 за один раз).
  Комірка `QUARANTINE` вже є: з неї нічого не можна видати (для браку та пошкодженого).
* **Settings → Suppliers / Categories / Units**: постачальники, категорії, одиниці виміру.
* **Products → New product**: матеріали.
* Початкові залишки: **Stock Movements → Stock adjustment**, причина **Opening Balance** (по кожній комірці).
  Так кожна одиниця на складі одразу має історію.
* **Users**: створіть облікові записи для працівників і призначте ролі.

## 3. Ролі

| Роль | Що може |
|---|---|
| Administrator | Усе, включно з користувачами, налаштуваннями та відновленням з копії |
| Store Manager | Усі складські операції, сторнування, коригування, override мінусових залишків, звіти, копії |
| Warehouse Operative | Goods In, Goods Out, переміщення, повернення, додавання фото/сканів, перегляд |
| Viewer | Лише перегляд і звіти |

Права кожної ролі можна змінити в **Users → Roles and permissions**.

## 4. Головні правила програми

* **Залишок змінюється тільки через документ** (Goods In, Goods Out, повернення, переміщення, коригування,
  виробництво). Кожен рух записується назавжди: хто, коли, звідки, куди, скільки, за яким документом.
* **Проведений документ не редагується і не видаляється.** Помилку виправляють кнопкою "Reverse…"
  із зазначенням причини: створюється дзеркальний рух, а оригінал залишається в історії.
* **Мінусовий залишок заблоковано.** Менеджер або адміністратор може провести видачу з override,
  але програма вимагає причину і записує її в журнал.
* **Одну накладну не можна внести двічі**: "DN 7781", "DN-7781" і "dn7781" від того самого постачальника
  програма вважає однією накладною.
* Товари, постачальники, комірки й об'єкти не видаляються, а деактивуються (історія залишається цілою).
  Товар із залишком у будь-якій комірці архівувати не можна: спочатку перемістіть або спишіть залишок.
* **Подвійне проведення неможливе**: повторне натискання "Post" або Ctrl+S не створює другий документ.
  Якщо на той самий об'єкт за останні 2 години вже видано точно ті самі матеріали, програма перепитає.
* **Повернення з об'єкта** не може перевищувати видане на цей об'єкт (менеджер може підтвердити виняток).

## 4a. Нове у версії 1.1

* **Stocktake (інвентаризація)**: створіть підрахунок для зони або складу, комірник вносить фактичну
  кількість (без підказки системної), менеджер бачить різницю, перевіряє і затверджує. Коригування
  проводяться автоматично з причиною "Stock count". Якщо під час підрахунку в комірці був рух,
  затвердження блокується до перерахунку.
* **Сканер штрихкодів**: у рядках документа скануйте код + Enter, курсор переходить у кількість,
  ще Enter і новий рядок. Шукається внутрішній код, штрихкод, потім код постачальника.
* **Low Stock / Reorder List**: статуси OK / LOW / OUT, згруповано за постачальником, сума замовлення.
* **Dashboard → Needs attention**: від'ємні залишки, товари OUT/LOW, інвентаризації на затвердження,
  накладні без скану, override за тиждень. Подвійний клік відкриває потрібний екран.
* **Project Material History**: звіт про всі видачі й повернення по об'єкту.
* Накладній після проведення можна змінити лише PO / примітки (з записом у журнал).
* Повний звіт тестування: [`docs/QA_REPORT.md`](docs/QA_REPORT.md).

## 4b. Нове у версії 1.2: пошук і фільтри

* **Search** (Ctrl+K або Ctrl+F з будь-якого екрана): один рядок для коду, штрихкоду, назви,
  постачальника, бренду, комірки, проєкту, номера накладної, PO. Регістр і пробіли в кодах не важливі:
  `h 3311` знайде H3311. Сканер працює в тому ж полі.
* Вкладки **Products** і **Transactions**, кнопки швидких фільтрів (In Stock, Low Stock, Recently
  Received...), **Advanced Filters** (товар, залишок, місце, постачальник, проєкт, тип руху,
  документи, дати). Активні фільтри видно як чипи, × прибирає, Clear All Filters прибирає всі.
* **Saved searches** для пошуків, що повторюються, і список останніх пошуків.
* Нові картки: товар (Overview: усі комірки і загальна кількість), комірка (вміст, рухи в / з),
  проєкт (Material Summary: видано, повернено, нетто), постачальник (товари, історія поставок).
* Інструкція з прикладами і заміри швидкодії на 10,000 товарів / 100,000 рухів:
  [`docs/SEARCH.md`](docs/SEARCH.md).

## 4c. Нове у версії 1.3: історія не губиться при видаленні

* Кожна операція запам'ятовує, **як усе називалося в той момент**: товар (код і назва), комірки
  «звідки / куди», проєкт, постачальник, користувач. Якщо пізніше перейменувати чи прибрати комірку,
  проєкт, товар або постачальника, стара історія показує саме те, що було.
* Кнопка **Delete** (комірка, товар, проєкт, постачальник) сама вибирає безпечний варіант:
  ніколи не використаний запис видаляється назавжди; запис з історією **прибирається з активного
  використання** (зникає зі списків вибору, нові операції заборонені), а вся історія лишається.
  Поки в комірці є товар або вона в незавершеній інвентаризації, видалити її не можна. Програма
  скаже, що саме заважає.
* **Restore** повертає запис у роботу; старі операції не змінюються.
* Проєкти: **Mark completed** (більше не видно у виборі, нові видачі заборонені, повернення
  залишків дозволене) і статус **Archived**. У пошуку вони позначені як *Historical Project*, а
  архівні комірки як *Historical Bin*. Картка архівної комірки показує поточний залишок, кількість
  рухів і повну історію.
* Хто, коли і чому видалив, архівував чи відновив, записується в журнал аудиту.
* Подробиці: [`docs/HISTORY.md`](docs/HISTORY.md).

## 4d. Нове у версії 1.13: нова структура меню і екранів

* Меню зліва: HOME / WAREHOUSE / OPERATIONS / PROJECTS / PURCHASING, а рідкісне згорнуте в MORE і ADMIN.
  Зверху завжди пошук (Ctrl+K) і кнопки Goods In (F2), Goods Out (F3), Transfer (F4).
* Dashboard показує один список ACTION REQUIRED: лише проблеми, від найважливіших. Клік відкриває
  екран уже з потрібним фільтром.
* Проєкт: Required / Reserved / Issued / Returned / **Remaining** в одній смужці, Goods Out прямо з картки.
* Імпорт Excel з порівнянням ревізій (Added / Removed / Changed). Залишок складу імпорт не змінює ніколи.
* Чернетки Goods In (Save Draft): незакінчену доставку можна дописати пізніше, склад вона не змінює.
* Подробиці і відповіді на питання перевірки: [`docs/UI_REFACTOR.md`](docs/UI_REFACTOR.md).

## 4f. Нове у версії 1.15: Project Tree (Менеджер → Проєкт → Блок → Рівень → Юніт → Матеріали)

* Новий екран **PROJECTS ▸ Project Tree**: дерево менеджерів, їхніх проєктів, юнітів (Kitchen K01 × 24)
  і матеріалів кожного юніта (існуючі товари зі складу + кількість на 1 юніт, VPK код).
* Необов'язкові **Блоки** і **Рівні** між проєктом і юнітами (Block A → Level 1 → Kitchen K01 × 24).
  **Duplicate Level** копіює цілий поверх з юнітами і матеріалами.
* Потреба рахується сама: кількість юнітів × кількість на юніт, по юніту, рівню, блоку, проєкту, менеджеру і всіх
  відкритих проєктах (**Material Demand...**). Нічого не зберігається окремо і склад не змінюється.
* Зміни прямо в дереві (подвійний клік), на панелі праворуч або через меню **⋯** / праву кнопку.
* Видалення менеджера ніколи не видаляє проєкти. Імена з поля «Project manager» стають менеджерами
  автоматично при оновленні.
* Подробиці: [`docs/PROJECTS.md`](docs/PROJECTS.md).

## 5. Де лежать дані і резервні копії

| Що | Де |
|---|---|
| База даних, фото, скани, журнали | `%LOCALAPPDATA%\StoreWMS` |
| Резервні копії | `Документи\StoreWMS Backups` (змінюється в Settings) |

* Копія створюється **автоматично при кожному закритті програми** (зберігаються останні 30).
* **Settings → Backup and restore → Back up now**: ручна копія (не видаляється автоматично).
* Копія це один `.zip`: база + всі фото та скани. Тримайте папку копій на іншому диску, флешці або в OneDrive.
* Відновлення: **Settings → Backup and restore → Restore…**. Перед відновленням програма сама робить
  страхувальну копію поточних даних.
* **Settings → Data check** перевіряє файл бази, зв'язки, відповідність залишків історії рухів і наявність файлів.

Перевірка без запуску вікна (для підтримки): `StoreWMS.exe --self-test`.

## 6. Кілька комп'ютерів (наступний етап)

Зараз база локальна (SQLite): найкраще працює на одному комп'ютері складу. Програма вже готова до спільної
бази PostgreSQL на сервері: у файлі `%LOCALAPPDATA%\StoreWMS\config.json` вказується
`"database_url": "postgresql+psycopg://wms@server/wms"`, а `"attachments_dir"` вказує на мережеву папку.
Код міняти не потрібно; потрібні лише сервер і драйвер `psycopg`.

## Для розробника

```
python -m venv .venv && .venv\Scripts\activate
pip install -r requirements-dev.txt
python run.py                     # запуск з вихідного коду
set QT_QPA_PLATFORM=offscreen && python -m pytest -q   # 104 автотести
ruff check wms tests              # перевірка стилю
python -m tools.generate_test_data D:\perf   # тестова база: 10k товарів, ~100k рухів
python -m tools.perf_check D:\perf --ui      # заміри швидкості на ній
```

Структура (три шари, екран ніколи не звертається до бази напряму):

```
wms/
  core/        переліки, права, формати UK (дати DD/MM/YYYY, £), винятки
  db/          моделі SQLAlchemy, міграції Alembic, початкові дані
  services/    бізнес-логіка: stock_engine (єдине місце, що змінює залишки), goods_in, goods_out,
               stock_ops, production, sites, reports, backup, audit, users...
  exporters/   Excel / CSV / PDF
  ui/          екрани PySide6 (pages/), діалоги (dialogs/), спільні віджети (widgets/)
tests/         автотести бізнес-логіки та інтерфейсу
packaging/     PyInstaller (StoreWMS.spec) і Inno Setup (installer.iss)
```

Зміна схеми бази: змініть модель у `wms/db/models`, потім
`alembic -c wms/db/migrations/alembic.ini revision --autogenerate -m "опис"` (або напишіть міграцію вручну
в `wms/db/migrations/versions`). При запуску програма сама оновлює базу до останньої версії.
